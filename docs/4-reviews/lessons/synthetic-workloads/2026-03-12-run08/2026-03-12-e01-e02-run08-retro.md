## Summary

Run 8 produced 5 markdown documents from a synthetic content workload across 2 epics (3 + 2 stories). The primary test objective was validating `isolation: "worktree"` for parallel builder dispatch, the top open defect from Run 7 (`c249257`). **Worktree isolation succeeded** — all 3 parallel builders in Wave 1 produced branches containing only their own files, with zero workspace collision. One story (E01-S01) required a fix cycle after the reviewer caught 9 sentences where 4-6 were specified. All 5 stories passed review and merged cleanly.

## What Worked

### 1. Worktree Isolation Eliminates Workspace Collision (Primary Test Result)

All 3 parallel builders in Wave 1 ran with `isolation: "worktree"` and each produced a branch containing only its expected file. This is verified by the reviewer acceptance criterion "Story branch contains ONLY this file" passing on all three stories (#7, #8, #9). The workspace collision defect from Run 7 (`c249257`, flagged as risk in Run 4) is confirmed fixed. The git safety conventions around chaining `git checkout && git add && git commit` in a single bash call (documented in CLAUDE.md) become a defense-in-depth measure rather than the primary isolation mechanism.

### 2. Reviewer Caught a Genuine Acceptance Criteria Violation

The reviewer on E01-S01 (#7) correctly identified that the narrator observation contained 9 sentences when the acceptance criteria specified 4-6. This was caught on the first review pass, and the fix cycle (builder-haiku re-dispatch) successfully reduced the count to 6 sentences in commit `12cb918`. The review-fix-rereview loop worked as designed.

### 3. Model Routing Worked Correctly Across All Difficulty Levels

All three difficulty levels were exercised: haiku for easy (E01-S01, E01-S02), sonnet for medium (E01-S03, E02-S01), and opus for hard (E02-S02). Each model completed its task successfully. Haiku was notably faster on easy tasks (802 tokens/s on E01-S02) but used significantly more tokens than sonnet (~103K vs ~29K), consistent with prior observations that cheaper models compensate with more turns.

### 4. Parallel Dispatch Achieved 3x Speedup

Wave 1's three parallel builders completed in 3m 20s (wall clock) versus 10m 8s sequential — a 3.0x speedup. This matches the theoretical maximum for 3 parallel tasks where the longest task dominates.

## What Didn't Work

### 1. Builder in Worktree Didn't Push to Remote

E01-S02's builder (haiku, worktree isolation) did not push its story branch to the remote from within the worktree. The orchestrator had to manually push the branch before merging. This suggests that worktree-isolated builders may not have the same remote-push behavior as main-tree builders, or the builder agent's instructions don't explicitly cover pushing from worktrees. This is an operational gap — if the orchestrator hadn't caught it, the branch would have existed only locally.

### 2. Worktree Left Untracked Files in Main Working Tree

After worktree-dispatched builders completed, an untracked file was left in the main working tree that blocked subsequent merge operations. The orchestrator had to run `rm -rf` cleanup before proceeding. This is a worktree lifecycle management issue — the worktrees themselves were cleaned up, but side effects persisted in the primary checkout.

### 3. GitHub API Rate Limit During E02-S02 Board Status Update

During the E02-S02 dispatch, a GitHub API rate limit hit during the board status update (`item-set-status.sh`). The orchestrator retried after a 30-second delay and succeeded. The `item-set-status.sh` script does handle retries, but the rate limit itself is a recurring risk when many board transitions happen in quick succession (14 dispatches generate significant API traffic).

### 4. Haiku Token Consumption Disproportionately High

Builder-haiku on E01-S01 consumed 211K tokens (across initial build + fix cycle) for a single markdown file — more than 5x what builder-sonnet used for E01-S03 (30K tokens, a more complex story). Even E01-S02 (haiku, no fix cycle) used 103K tokens versus sonnet's 29K. This pattern is consistent with Run 7 observations: haiku is cheaper per token but uses far more tokens, partially negating the cost advantage. E01-S01 cost ~$0.42 total versus E01-S03 at ~$0.18.

## Key Learnings

### For Builders

1. When running in a worktree, explicitly push the story branch to remote before signaling completion. The main working tree and worktree share `.git`, but push behavior may differ based on how the agent's cwd is set.
2. Haiku builders should be monitored for token overuse on content-creation tasks. The model compensates for lower capability by doing more tool calls and turns, which can make "easy" stories cost more than "medium" ones.

### For the Orchestrator

1. After worktree-dispatched builders complete, verify that no untracked files were left in the main working tree before proceeding to merges. A `git clean -fd` check (dry run first) would catch this.
2. When dispatching many agents in rapid succession, budget for GitHub API rate limits. The 14-dispatch run hit a rate limit on status updates. Consider batching board transitions or adding short delays between sequential dispatches.

### For the Workflow

1. **Worktree isolation is production-ready.** Run 8 confirms that `isolation: "worktree"` eliminates workspace collision for parallel builders. The CLAUDE.md convention added after Run 7 is validated. The older git-safety conventions (chain checkout+add+commit) remain as defense-in-depth but are no longer the primary isolation mechanism.
2. **Haiku cost efficiency on content tasks is questionable.** Across Run 7 and Run 8, haiku consistently uses 3-5x more tokens than sonnet for comparable tasks. For markdown-only stories with no code, sonnet may be more cost-effective even at a higher per-token rate. Consider updating model routing guidance to note this trade-off.
3. **Fix cycles work reliably.** The reviewer correctly caught a spec violation, the builder fixed it in one cycle, and the re-review approved. The max-2-cycle constraint was not needed (resolved in 1 cycle).

## Recommendations

1. **Add worktree cleanup step to orchestrator post-dispatch** — After all worktree-dispatched builders complete, the orchestrator should check for and remove stale files in the main working tree. (Proposed as convention change.)
2. **Document builder remote-push requirement for worktree mode** — Builder agent instructions should explicitly state that the story branch must be pushed to remote, regardless of whether the builder is running in the main tree or a worktree. (Proposed as convention change.)
3. **Reconsider haiku for content-creation tasks** — Haiku's token consumption on markdown writing tasks (100K-210K) versus sonnet (28K-30K) suggests that the cost advantage of haiku ($0.21 vs $0.18 per story) is marginal or negative when fix cycles are factored in. This is an observation for future model routing decisions, not a convention change — the routing is already based on difficulty labels, and the planner controls the labels.
4. **GitHub API rate limit resilience** — The `item-set-status.sh` script already retries, which handled the rate limit gracefully. No convention change needed, but the orchestrator should log rate limit events for telemetry tracking.
