## Overview

**Blocked by:** none

The workflow's CLI scripts (\`scripts/item-*.sh\`, \`scripts/state.sh\`, etc.) have grown organically with inconsistent argument interfaces and are all written in bash. This backlog item covers two concerns:

### 1. Inconsistent argument interfaces

An audit of 19 scripts reveals three different patterns:

| Pattern | Scripts | Example |
|---------|---------|---------|
| **Pure positional** (8) | item-close, item-comment, item-link-child, item-set-status, item-review, check-board-drift, batch-set-status, validate-logs | \`item-comment.sh <N> <body>\` |
| **Hybrid** (6) | item-get, item-start, item-append-body, dispatch-story, cleanup-post-merge, dispatch-workflow | \`item-start.sh <N> --model sonnet\` |
| **Pure flags** (5) | item-create, item-list, item-telemetry, reconcile-board, state.sh | \`item-create.sh --title "..." --body "..."\` |

The hybrid pattern is the most problematic — positional args must come before flags, which creates ordering constraints (e.g., \`--updated-by\` can't be placed before a multi-line body argument in \`item-append-body.sh\`). New features requiring additional parameters force awkward positional-then-flag ordering.

The newer/more complex scripts (item-create, item-telemetry, state.sh) already use pure flag parsing — this should be the standard.

### 2. Language evaluation

All scripts are bash. This was pragmatic for the early workflow (simple wrappers around \`gh\` and \`git\`), but as the scripts have grown more complex (JSON parsing with \`jq\`, state file management, telemetry computation, dual-write adapters), bash shows limitations:

- String manipulation and escaping (especially in \`eval\`'d functions in the GitHub adapter)
- Error handling (\`set -euo pipefail\` catches some issues but not all)
- Testing (the test scripts are bash too, with manual assertion functions)
- Data structures (associative arrays are limited, no native JSON)
- The PM adapter layer uses complex patterns (function renaming, dual-write wrappers) that are fragile in bash

The designer should evaluate whether some or all scripts should migrate to a different language (Python, Node.js, or other options), considering:
- Portability (must work on macOS and Linux with minimal dependencies)
- Ergonomics for the primary operations (GitHub API, JSON manipulation, file I/O, git operations)
- Integration with the existing bash ecosystem (some scripts may stay bash)
- Migration cost vs long-term maintenance benefit
- Whether a hybrid approach makes sense (bash for thin wrappers, another language for complex logic)

\`compute-dispatches.py\` already uses Python for the most complex computation — this may be a signal about where the boundary should be.

## Acceptance criteria

- [ ] Design doc evaluates language options with trade-offs (not just bash vs one alternative)
- [ ] All scripts migrated to consistent flag-based argument parsing
- [ ] Argument ordering is flexible (flags can appear in any position)
- [ ] Usage/help output (\`--help\`) standardized across all scripts
- [ ] Backward compatibility considered (existing agent instructions reference current interfaces)
- [ ] Agent files updated to reflect any interface changes
