## Overview

**Blocked by:** #116

The Workflow Runtime Service (BL#116) has a sync engine that pushes local changes to GitHub (SQLite → GitHub). But there is no reverse sync — the database cannot pull current state from GitHub.

## Problem

The database is currently seeded from `.workflow/items/` files, which contain stale local PM state. Statuses, comments, and labels may not match what's on the GitHub project board. When a user starts the dashboard for the first time (or after a database reset), they see outdated data.

## Scope

- Implement a "pull from GitHub" sync that fetches all issues (or a filtered subset) from the GitHub repo via `gh` CLI and upserts them into the SQLite database
- Should run on first startup (when database is empty) as an alternative to the file-based seed
- Should be runnable on demand (e.g., `bun run server/src/index.ts sync` or via API endpoint)
- Handle: issue state, board status (from project board), labels, comments, parent-child hierarchy (sub-issues)
- Conflict resolution: GitHub is the source of truth when pulling — overwrite local state
- Rate limit awareness: fetching 300+ issues requires pagination and may hit the 5000 points/hour GraphQL budget

## Non-Goals

- Real-time bidirectional sync (webhooks) — that's a future concern
- Replacing the push direction (SQLite → GitHub) — that already works via the sync queue
