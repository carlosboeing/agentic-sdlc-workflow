## Overview

**Blocked by:** none

The Agent tool returns significantly richer telemetry than we currently capture. We only use 3 of ~10 available fields, leading to inaccurate cost estimates, misleading Gantt charts, and the inability to distinguish stalled sessions from productive work.

## Problem

### Missing metrics

Research (confirmed via official Claude Agent SDK docs and GitHub issues) shows the Agent tool's ResultMessage includes:

| Field | Available | Currently captured | Impact of gap |
|-------|-----------|-------------------|---------------|
| \`duration_ms\` | Yes | Yes | Wall-clock (includes stalls) |
| \`duration_api_ms\` | Yes | **No** | API time only — solves the stall problem |
| \`total_tokens\` | Yes | Yes | Aggregate only |
| \`input_tokens\` | Yes | **No** | Needed for accurate cost calculation |
| \`output_tokens\` | Yes | **No** | Needed for throughput calculation |
| \`total_cost_usd\` | Yes | **No** | Direct cost from platform — eliminates rate estimation |
| \`num_turns\` | Yes | **No** | Agentic turn count |
| \`tool_uses\` | Yes | Yes | Already captured |

### Gantt stall visualization

The Gantt chart becomes unreadable when a dispatch is stalled (rate-limited, API errors). Example from backlog 243: E02-S01 builder reported 490m wall-clock but only 85K tokens (~5m of productive work). The 490m bar dominates the chart and makes all other tasks invisible.

\`duration_api_ms\` would solve this — it measures API roundtrip time excluding stalls and idle waiting. For stalled dispatches, the Gantt should use \`duration_api_ms\` for bar width, with an annotation showing the wall-clock gap.

### Cost estimation accuracy

We currently estimate costs using \`total_tokens × blended_rate_per_model\`. But:
- \`total_tokens\` doesn't split input vs output (which have very different rates)
- We fetch and cache pricing, but apply a blended rate that's inherently inaccurate
- \`total_cost_usd\` is available directly from the platform — no estimation needed

## Proposed Solution

1. **Capture all available fields** — Update orchestrator state file dispatch entries to include \`duration_api_ms\`, \`input_tokens\`, \`output_tokens\`, \`total_cost_usd\`, and \`num_turns\`
2. **Update telemetry scripts** — \`item-telemetry.sh\` and \`compute-dispatches.py\` should use the richer data when available
3. **Fix Gantt stall visualization** — Use \`duration_api_ms\` for Gantt bar width when available; fall back to token-estimated duration for stalled dispatches when \`duration_api_ms\` is not available
4. **Use \`total_cost_usd\`** — When available, use direct platform cost instead of rate-estimated cost

## Key question: Are these fields surfaced in Claude Code's conversational interface?

The Agent SDK's ResultMessage contains these fields, but Claude Code's \`<usage>\` block currently only surfaces \`total_tokens\`, \`tool_uses\`, and \`duration_ms\`. Investigation needed:
- Are the additional fields available but not displayed?
- Can they be captured via OTEL telemetry?
- Can the subagent self-report them in its text response?
- Is there a Claude Code setting to expose more usage data?

This question must be answered during the design phase. Do NOT assume — research official docs and test.

## Evidence

- Backlog 243 Gantt chart: 490m stalled bar makes chart unreadable
- BL#227 Gantt chart: 91m stalled bar (same problem, documented in workflow optimization analysis § 12.2)
- 14+ runs of telemetry using blended rate estimation instead of actual costs
- Agent SDK docs confirm \`duration_api_ms\`, \`input_tokens\`, \`output_tokens\`, \`total_cost_usd\` exist in ResultMessage
