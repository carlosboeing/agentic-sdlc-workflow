## What Worked

### 1. Single-PR Workflow Executed Cleanly

The entire backlog item — design doc, plan, 2 epics with 5 stories, lessons — was built on the `backlog/162-cat-performance-review` integration branch with design/plan PRs targeting the integration branch (not main). The branch hierarchy worked as designed: story branches merged into epic branches, epic branches merged into the integration branch, and the integration branch will become a single PR to main. This is the first successful end-to-end test of the workflow introduced in #161.

### 2. Three-Story Parallel Dispatch Worked Perfectly

Wave 1 dispatched all three E01 stories (#168, #169, #170) in parallel across two model tiers (haiku and sonnet). All three completed successfully with no merge conflicts, achieving a 2.2x speedup over sequential execution. The parallel stories wrote to separate files (`review-wfh-human.md`, `review-early-riser.md`, `review-dog-owner.md`) as the plan intended, eliminating any contention risk.

### 3. Zero Fix Cycles Across All Stories

All 5 stories passed review on the first attempt. The reviewer issued no critical issues or blocking warnings. The two warnings raised (#169 missing trailing newline, #170 word count 3 over) were both non-blocking. This suggests the plan's acceptance criteria were precise enough for builders to implement correctly on the first pass.

### 4. Haiku Efficiency for Easy Stories

The two haiku-routed easy stories (#168, #169) consumed 2-3x more tokens than the sonnet/opus stories (111K and 109K vs 37-38K) but completed faster in wall-clock time (1m 46s - 1m 58s vs 2m 59s - 3m 6s) at one-third the per-token cost. The net cost per easy story (~$0.22) was comparable to medium stories (~$0.22-0.23), making haiku routing cost-effective for simple tasks.

### 5. State File Provided Complete Dispatch Telemetry

The orchestrator state file (`.claude/state/162/orchestrator.json`) captured all 12 dispatches (designer, planner, 5 builders, 5 reviewers) with model, duration, tokens, tool uses, and result for each. This made retro data gathering straightforward — no need to reconstruct telemetry from scattered issue comments.

## What Didn't Work

### 1. Design/Plan Issues Stuck in "In Progress" on the Board

After auto-merging design PR #164 and plan PR #173, the orchestrator called `issue-merged.sh` for issues #163 and #165, but the script could not find them on the project board. The `gh project item-list` query returned stale data immediately after `gh project item-add`. Both issues were closed but remained stuck at "In Progress" on the board instead of moving to "Done".

**Root cause:** Race condition between `gh project item-add` and `gh project item-list` — the API does not guarantee immediate consistency. No retry logic exists in `issue-merged.sh`.

**Impact:** Board accuracy was degraded. The issue was noticed and a lesson file was written (`2026-03-10-s00-design-plan-board-status-gap.md`), but the board was not manually corrected during the run.

*Reference: lesson file `docs/4-reviews/lessons/162-cat-performance-review/e00-setup/2026-03-10-s00-design-plan-board-status-gap.md`*

### 2. Stale Status Option ID in Planner Agent File

The planner agent file contained a "Planned" status option ID (`2b7091c1`) that did not match the project board's actual ID (`cf183d2a`). All 7 `item-edit` calls for setting story statuses to "Planned" failed before the planner retried with the correct ID from CLAUDE.md.

**Root cause:** The planner agent file duplicates status option IDs from CLAUDE.md, and the copy diverged when the project board was reconfigured.

**Impact:** Extra API calls and wasted time during plan creation. The planner recovered by falling back to CLAUDE.md values, but this added latency to the plan phase (contributing to the 5m 34s plan duration vs 3m 28s design).

*Reference: lesson file `docs/4-reviews/lessons/162-cat-performance-review/e00-setup/2026-03-10-s00-stale-status-option-id.md`*

### 3. GitHub GraphQL Rate Limit Exhaustion in Wave 3

The user reported that the GitHub GraphQL rate limit was exhausted during Wave 3, affecting builder and telemetry scripts. This is not captured in the state file or issue comments (the scripts succeeded after retries or the orchestrator absorbed the delay), but it represents a risk for runs with more stories or tighter API budgets.

**Root cause:** The cumulative effect of board management operations across design, plan, and 3 build waves — each involving `item-add`, `item-list`, `item-edit`, and `addSubIssue` GraphQL mutations.

**Impact:** Unknown delay. No telemetry data captures GraphQL rate-limit waits specifically. The issue was observed by the user but not automatically detected or logged by the orchestrator.

However, this was the **first run after the single-PR workflow convention was adopted** (commit `29a593c` on main). The entire run served as the validation of that convention.

## Key Learnings

### For Builders

1. **Haiku builders consume 3x more tokens than Sonnet/Opus for comparable tasks** (111K vs 38K), but at 1/3 the per-token cost, the net cost is equivalent. The speed advantage (951-1027 tok/s vs 202-214 tok/s) makes haiku a good choice for genuinely simple stories.
2. **Markdown-only stories complete in under 2 minutes** even with the overhead of reading issue context, checking out branches, and running the test suite. The floor for builder agent time appears to be ~1m 45s regardless of task simplicity.

### For the Orchestrator

1. **Board consistency after `issue-merged.sh` is not guaranteed.** The orchestrator should verify board state after calling the script and correct it if needed, particularly for design/plan issues that were recently added to the board.
2. **GraphQL rate limits are a real constraint** for runs with many stories. The orchestrator should track API call counts and introduce backoff or batching if nearing the limit.
3. **Sequential reviews after parallel builds add up.** The 3 sequential reviews after Wave 1 took ~3 minutes — nearly as long as the parallel build wave itself. Parallel review dispatch could further compress wall-clock time.

### For the Workflow

1. **The single-PR workflow works end-to-end.** The integration branch cleanly accumulated design, plan, lessons, and 5 stories across 2 epics. The branch hierarchy (story -> epic -> integration) merged without conflicts.
2. **Agent file convention drift is a recurring theme.** The stale option ID in the planner agent file is the same class of problem as previous runs where agent files fell out of sync with CLAUDE.md. The "propagate changes immediately" convention exists but is not enforced mechanically.
3. **Zero fix cycles suggests well-specified acceptance criteria** in the plan. The plan's per-story criteria were detailed enough (section names, word counts, tone requirements) that builders hit the mark on the first pass.

## Recommendations

1. **Add retry logic to `issue-merged.sh`** — Wait 2-3 seconds and retry the `item-list` query if the item is not found. This addresses the board consistency gap without requiring orchestrator-level workarounds. (Source: lesson `2026-03-10-s00-design-plan-board-status-gap.md`)

2. **Remove duplicated status option IDs from agent files** — Agent files should reference CLAUDE.md as the single source of truth for option IDs, or at minimum the orchestrator should validate agent file IDs against CLAUDE.md at session start. (Source: lesson `2026-03-10-s00-stale-status-option-id.md`) *Status: proposed as convention change below.*

3. **Add GraphQL rate-limit awareness to orchestrator** — Track cumulative API calls and introduce a warning/backoff when approaching the rate limit. This is an architectural change rather than a convention change, so it is flagged for the planner rather than proposed here.

4. **Consider parallel review dispatch** — Reviews for independent stories within the same wave could run in parallel, matching the parallelism of the build phase. This would compress Wave 1 from ~5.5 minutes (2.5m build + 3m review) to ~3.5 minutes (2.5m build + 0.75m parallel review). This is an orchestrator design decision, not a convention change.
