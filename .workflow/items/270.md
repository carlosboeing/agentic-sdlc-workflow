### Prompt Augmentation (design doc section 3.2)

The orchestrator constructs each builder's dispatch prompt in two parts:

**Part 1:** Standard builder prompt (unchanged)
**Part 2:** POST-BUILD LIFECYCLE section with either REVIEW or SKIP tier

REVIEW tier template:
```
=== POST-BUILD LIFECYCLE ===
After implementation is complete and item-review.sh has been called:

Review tier: REVIEW

1. Dispatch a reviewer agent on your branch:
   - Use: Agent tool, subagent_type: "reviewer", isolation: "worktree"
   - Prompt: "Review story #<N> on branch <branch>.
     Post findings as a comment on issue #<N>."

2. Read the reviewer's response:
   - If verdict is APPROVE or COMMENT: your work is complete. Return.
   - If verdict is REQUEST_CHANGES:
     a. Fix the issues on your branch (same branch, new commits)
     b. Push fixes: git push origin <branch>
     c. Re-dispatch the reviewer (same prompt as step 1)
     d. Maximum 2 fix cycles. After 2 REQUEST_CHANGES, return with
        status "fix_cycles_exhausted".

3. Include reviewer metrics in your final response:
   - reviewer_duration_ms: <from Agent tool result>
   - reviewer_tokens: <from Agent tool result>
   - reviewer_tool_uses: <from Agent tool result>
   - fix_cycles: <0, 1, or 2>
   - final_verdict: <APPROVE, COMMENT, or REQUEST_CHANGES>
```

SKIP tier template:
```
=== POST-BUILD LIFECYCLE ===
Review tier: SKIP
No per-story review required for this story. The PR review is the quality gate.
After implementation is complete and item-review.sh has been called, return.
```

### Review Tier Decision Logic (design doc section 4.2)

```
IF story has backlog label matching CFG_SKIP_REVIEW_REQUIRE_LABEL
   AND story difficulty <= CFG_SKIP_REVIEW_MAX_DIFFICULTY
   AND CFG_SKIP_REVIEW_ENABLED == true:
    review_tier = SKIP
ELSE:
    review_tier = REVIEW
```

### Virtual Reviewer Dispatches (design doc section 3.6 and 5.4)

For each story with review_tier REVIEW, record TWO dispatch entries:

1. Builder dispatch: full duration_ms and total_tokens from Agent tool result
2. Reviewer dispatch (virtual): metrics from builder's response text, with `nested_in: "builder-<model>"` field

Compute reviewer `started_at` as: builder's `started_at` + builder's `duration_ms` - reviewer's `duration_ms`

### Board Transitions (design doc section 3.7)

| Transition | Owner |
|-----------|-------|
| Ready -> In Progress | Orchestrator (before dispatch, unchanged) |
| In Progress -> In Review | Builder (via item-review.sh, unchanged) |
| Fix cycle: In Review -> In Progress | Builder (during fix cycle) |
| Final -> In Review | Builder (at end of lifecycle) |

Orchestrator verifies In Review after builder returns (defense-in-depth).
