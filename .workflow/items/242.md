## Overview

**Blocked by:** none

Fix two Gantt chart readability problems identified in the workflow optimization analysis (`docs/1-discovery/2026-03-19-workflow-optimization-analysis.md` § 12, § 13 items 3 and 6):

1. **Story code regression** — Gantt labels and breakdown table lost their story code prefixes (e.g., `E01-S02 Build (9m 3s)` became generic `Build (9m 3s)`)
2. **Compressed Gantt ("Work Timeline" mode)** — Sessions with interruptions (API errors, usage limits, interactive pauses) produce unreadable charts where 97% of the timeline is whitespace

Both issues are in `scripts/lib/compute-dispatches.py` and share the same Gantt generation code path.

## Problem 1: Story Code Regression

### What broke

The `_gantt_label_for_dispatch()` function (line ~708) supports story codes via `_build_story_labels()` (line ~675), producing labels like `E01-S02 Build (9m 3s)`. But recent runs show generic labels: `Build (9m 3s)`.

The `_build_story_labels()` mapping extracts story codes from the orchestrator state file's epic/story branch names (e.g., branch `e01-s02/destination-profiles` → code `E01-S02`). The mapping stopped populating for some dispatches — likely a regression in how the state file records dispatch metadata.

### Acceptance criteria

- [ ] Gantt labels include story codes for all builder, reviewer, and fix cycle dispatches: `E01-S02 Build (9m 3s)`, `E01-S02 Review (1m 10s)`, `E01-S02 Fix (3m 45s)`
- [ ] Breakdown table includes a Story column showing the story code (e.g., `E01-S02`)
- [ ] Design/plan/retro dispatches show descriptive labels (not story codes, since they're not per-story)
- [ ] Regression test: run `compute-dispatches.py --from-state` against an existing state file and verify labels

## Problem 2: Compressed Gantt ("Work Timeline" Mode)

### Evidence

BL#227 (Dual-Write PM) Gantt chart spans 00:00:00 to ~12:20:00 because of a ~9h gap from an API 529 error. Only ~40 minutes of that timeline is actual work. The chart is 97% whitespace with tasks after the gap compressed into unreadable slivers.

Additionally, BL#227's first builder (`Issue #233`) shows as a 91-minute bar but only consumed 82K tokens (~15 tok/s vs typical ~300 tok/s). The Agent tool's `duration_ms` includes pauses — usage limit waits, API throttling, and session interruptions are all counted. There's no separate "active compute time" metric.

A prior fix attempt (gap compression) was built and reverted (commits `4f51e4d` → `645be97`) because it interacted badly with the stalled duration problem. Both issues must be solved together.

Documented in lesson file: `docs/4-reviews/lessons/227-dual-write-pm/e00-setup/2026-03-19-s00-gantt-timeline-distortion.md`

### Proposed design

**X-axis = cumulative active time** (not wall-clock):
- Parallel tasks stacked at the same X offset (wave grouping preserved)
- Wave contribution to timeline = `max(duration_ms)` of parallel dispatches (critical path)
- The `_group_dispatches_by_parallel_wave()` function already identifies parallel waves — use `max(duration_ms)` per wave as the offset increment

**Pauses shown as indicators, not gaps:**
- Gaps > 5 minutes between waves → annotated marker line on the chart with a text note below (e.g., `⚠ 9h gap — API 529 overload`)
- Multiple dispatches of the same (issue, agent) consolidated into a single bar
- Stalled dispatches (< 50 tok/s throughput) flagged with a note

**Retain wall-clock mode as diagnostic:**
- `--gantt-mode work` (default) — cumulative active time
- `--gantt-mode wall-clock` — current behavior (absolute timestamps), for debugging rate limits

### Acceptance criteria

- [ ] Default Gantt mode shows cumulative active time, not wall-clock
- [ ] Pauses/interruptions > 5m shown as indicator markers with text annotation below the chart
- [ ] BL#227 state file produces a readable chart (not 97% whitespace)
- [ ] Stalled dispatches (< 50 tok/s) annotated
- [ ] `--gantt-mode wall-clock` retains current absolute-timestamp behavior
- [ ] Existing `--gantt-from-state` flag works with both modes
