## Overview

**Blocked by:** none

The local PM storage layer (\`.workflow/items/\`) currently uses flat markdown files — one file per work item. This doesn't scale. At 282+ items and growing 8-15 per backlog run, the folder will reach thousands of files within months. The designer should explore storage approaches that scale to tens of thousands of items while supporting the query patterns the workflow actually needs.

## Problem

1. **Flat folder doesn't scale** — \`.workflow/items/\` is a single directory with one file per item. At current growth rate (~15 items per backlog run, ~2-3 runs per week), we'll hit 1000+ files in months. File systems handle this, but human browsability, git operations, and grep-based querying degrade.

2. **No query capability** — Finding "all open stories for backlog 243" requires grepping across all files. Filtering by label, status, hierarchy, or relationship requires parsing YAML frontmatter from every file. This gets slower as the item count grows.

3. **No relationship model** — The backlog → epic → story hierarchy exists in GitHub's sub-issues but isn't queryable locally. Cross-referencing requires following issue numbers across files.

4. **Git compatibility unclear** — These files are currently committed to git on integration branches. But they're machine-generated mirrors of GitHub state, not human-authored content. The value of git-tracking them is questionable.

## Context

- The PM abstraction layer (backlog #109) provides the interface: \`pm_create_item\`, \`pm_get_item\`, \`pm_list_items\`, etc. The storage backend is an implementation detail inside \`adapters/pm/local/\`.
- The dual-write system (backlog #227) established "local always-on, external optional." The local store is the primary, GitHub is the external mirror.
- Current scripts are all bash, using \`jq\` for JSON and frontmatter parsing.
- The orchestrator state file (\`.agentic-workflow/runs/<N>/orchestrator.json\`) stores dispatch history and session data separately from PM items.

## Query patterns the workflow uses today

The designer should research what queries are actually performed against local items and optimize for those:

- Get item by number
- List items by label (e.g., \`backlog/243-*\`)
- List items by state (open/closed)
- List items by hierarchy level (backlog/epic/story)
- Get all children of a parent item
- Update item status/fields
- Bulk operations (batch status updates)

## What the designer should explore

The designer should research and evaluate storage approaches — do NOT constrain to any specific technology. Consider the full landscape: embedded databases, document stores, flat file reorganization, hybrid approaches, or anything else that fits the constraints. Research what other CLI tools, dev workflows, and local-first systems use for similar problems.

Key constraints to evaluate against:
- Must work as a local-first store (no network dependency)
- Must support the PM adapter interface (\`pm_*\` functions)
- Must handle the query patterns above efficiently
- Portability: should work on macOS and Linux with minimal dependencies
- The workflow scripts are primarily bash — consider the ergonomics of the chosen approach from bash
- Migration path from current flat files

## Acceptance criteria

- [ ] Design doc evaluates multiple storage approaches with trade-offs
- [ ] Chosen approach scales to 10,000+ items without degradation
- [ ] Query patterns above are supported efficiently
- [ ] Migration plan from current flat files
- [ ] PM adapter interface (\`pm_*\` functions) unchanged or backward-compatible
